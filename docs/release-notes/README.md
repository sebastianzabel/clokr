# Release Notes Corpus

This directory is the single source of truth for the German, customer-facing release notes of
Clokr. `apps/api/Dockerfile` bakes this directory into the API image (Plan 04 of Phase 110), and
`.github/workflows/release.yml` fills the GitHub Release body from the matching file in here
(Plan 05). GitHub is downstream of this directory, not the other way round (N-03): the direction
used to be "write on the GitHub Release, read it back later" — it is now "write the file here
first, GitHub and the image both read from it."

## File name

One file per published release: `v<major>.<minor>.<patch>.md`, e.g. `v1.9.18.md`. The version is
taken from the **filename**; the `## v<version> — <Titel>` headline on the file's first line must
agree with it — a mismatch is a copy-paste error, not a stylistic choice, and the parser
(`apps/api/src/utils/release-notes.ts`) throws on it rather than silently mislabeling an entry.

## Grammar

The parser implements exactly this fixed, project-owned grammar — not general CommonMark:

```markdown
## vX.Y.Z — <kurzer deutscher Titel>

<1–2 Sätze Einleitung.>

### Neue Funktionen

- <Bullet mit **fetten** Schlüsselbegriffen>

### Fehlerbehebungen

- <Bullet>

---

_<optionaler Audit-Hinweis>_
```

Four STRUCTURAL rules, and only these four give a construct a distinct data shape:

1. Exactly one `## v<version> — <Titel>` line — always the first non-empty line of the file.
2. `### <Heading>` opens a section (e.g. "Neue Funktionen", "Fehlerbehebungen", "Sicherheit").
3. `- <text>` is a bullet inside the current section.
4. `**bold**` inside a bullet marks a bold span (`{ text, bold: true }`).

Everything else — including a `[link](url)` or a `> [!CAUTION]` blockquote callout — is carried
as literal text and displayed literally, not rendered as a link or a callout. That is a
deliberate, documented limitation: it is what removes the XSS surface by construction (N-08/AK-13)
rather than by sanitising untrusted markup. If a body needs to draw attention to something, say so
in prose; do not rely on Markdown syntax beyond the four rules above to carry meaning in the
rendered dialog.

**Cosmetic exception (Phase 110-07 checkpoint fix):** inline emphasis markers that carry no
structural meaning above — `**bold**` outside a bullet (e.g. in the intro paragraph), single-`*`
italic, and inline code wrapped in a backtick pair — are stripped down to their plain content
wherever they appear, instead of being displayed with their raw punctuation. This was found live:
the intro paragraph and several "Betrieb & Migration" bullets in `v1.9.18.md` showed literal `**`
and backtick characters in the running drawer. This stripping never produces a new data shape or
any HTML — it only removes delimiter characters — so it does not weaken the XSS-by-construction
guarantee above. A genuinely unrecognised construct (`[link](url)`, `> [!CAUTION]`) is still left
completely untouched, punctuation and all.

## When to write one

Write the file **before** merging the release-please PR — see `docs/release-process.md` for where
this step sits in the release order. The image build and the GitHub Release publish step both
depend on the file already being on `main` at merge time; there is no "write it afterwards" path
any more (see N-01/N-02 in the Phase 110 context: the previous "write it on GitHub after the
image is already built" order was not buildable, because the image build happens
before a human would sit down to write the notes).

## This directory is not `CHANGELOG.md`

`CHANGELOG.md` is generated by release-please from Conventional Commit messages: it is English,
cut by commit rather than by user-visible topic, and includes a refactoring section irrelevant to
an end user. This directory follows `docs/RELEASE_NOTES_TEMPLATE.md` instead: German,
user-oriented, grouped by topic, PII-free, with the fixed section headings from the template
(Neue Funktionen / Verbesserungen / Fehlerbehebungen / Anzeige & Bedienung / Sicherheit /
Betrieb & Migration / Achtung). Both files can describe the same release; they answer different
questions for different audiences and neither is derived from the other (D-02/AK-02).

## Backfill note

The 22 files present as of Phase 110 (`v1.8.26.md` … `v1.9.18.md`) are a one-off backfill of
already-published GitHub Release bodies (N-05/AK-16), pulled verbatim via
`gh release view <tag> --json body`. They were not rewritten to conform to this README — they
already conformed, because they were written against `docs/RELEASE_NOTES_TEMPLATE.md` in the
first place. The one exception is `v1.9.15.md`, whose GitHub Release body opens with a
`> [!CAUTION]` withdrawal notice ahead of the templated headline; per Revisionssicherheit, only
its first line was changed (to the release's actual title, the withdrawal notice itself) so the
file satisfies the one-headline-per-file naming rule without deleting or rewording the original
withdrawal text.
